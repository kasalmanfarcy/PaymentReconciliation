# ReconFlow — Phase Plans

**Date:** 2026-11-01

[TASKS.md](../TASKS.md) lists *what* to build. The files here explain *how* to build it, *why* it is built that way, and which concepts each phase teaches. Each phase plan follows the same layout:

1. **Goal**: what exists at the end, and the demo that proves it
2. **Concepts to understand first**
3. **Starting point**: what the repo already has
4. **Step by step**: one section per task ID, each with *What*, *Why*, *How*, *Pitfalls* and *Done when*
5. **Testing strategy**
6. **Exit criteria checklist**
7. **Interview questions this phase prepares you for**
8. **Common mistakes**

**Three ordering exceptions to the table:**

1. **M4 is built partway through M3.** Login has to write audit events, so the order is M3.1, M3.2 and the M3.4 interfaces, then all of M4, then M3.3 and the rest of M3 (phase-M3 §4).
2. **Pull M2.16 (Testcontainers) forward into M0.** Until it lands, `./mvnw test` fails on a fresh clone, because the only test needs a running Postgres (phase-M0).
3. **Build the partition-maintenance job (phase-M9, "new" items) no later than M5.** V1 created monthly partitions only up to 3 months after it was applied. Rows dated after that land in the default partition, and a monthly partition can't be created for a range while rows for it sit there.

## Decisions every phase shares

Every phase plan assumes these decisions. M1 records each one in an ADR. If one changes, update the ADR first, then every plan that depends on it.

| Area | Decision |
|---|---|
| Stack | Java 25, Spring Boot 4.1.2, PostgreSQL 16, Maven wrapper. Root package `com.reconflow.paymentreconflow`. |
| Schema | V1–V3 already create most tables. Applied migrations are never edited; changes go in the next free `V` number. |
| IDs | UUIDv7, generated by the application. |
| Money | `BigDecimal` ↔ `NUMERIC(19,4)`. Amounts with more than 4 decimal places are rejected. Compare with `compareTo`, never `equals`. |
| Architecture | Modular monolith with packages `organization`, `ingestion`, `ledger`, `reconciliation`, `exceptions`, `reporting`, `audit`, `shared` and `security`. Boundaries are enforced by Spring Modulith. |
| Profiles | Role profiles `api` and `worker` in one jar, plus environment profiles `local`, `test` and `prod`. |
| Async work | Imports and runs return `202 Accepted`. Work runs from the DB `job` table, claimed with `FOR UPDATE SKIP LOCKED`. Jobs have leases and heartbeats, each organization can have at most 2 jobs running, and a sweeper recovers stuck jobs. The queue is built in M5 and hardened in M9. |
| Files | `FileStorage` on S3-compatible storage, with MinIO locally. |
| Duplicate files | A SHA-256 content hash with a unique constraint. A duplicate returns `409` with `existingBatchId`. Failed batches are retried in place and never re-uploaded. |
| Run idempotency | Uses the `Idempotency-Key` header, or a key derived from the org, period, sources and currency. The same key returns the existing run. |
| Concurrency | Exceptions carry `@Version`, and clients send `If-Match`. A missing header returns `428`; a stale version returns `409`. |
| Errors | RFC 9457 `ProblemDetail` with `type` set to `https://reconflow.dev/problems/<code>`, plus `code` and `requestId`. |
| Tenancy | The `X-Organization-Id` header selects the org, and a request-scoped `TenantContext` holds it. Every query takes `organizationId`, PostgreSQL RLS is a second layer, and another tenant's IDs return `404`. |
| Authorization | Code checks permissions, never role names ([authentication.plan §5](authentication.plan)). |
| Matching | Set-based SQL that Java orchestrates, chunked by day with a checkpoint. |
| Imports | Streamed CSV, committed every 5,000 rows, with a `last_committed_row` checkpoint. |
| Audit | `AuditService.record(...)` runs in the caller's transaction (`Propagation.MANDATORY`). DB triggers keep `audit_event` append-only. |
| Module ownership | `organization` owns `organization`. `security` owns `app_user`, `membership` and `refresh_token`. The `TenantContext`/`CurrentUser`/`TenantScope`/`Permission` interfaces live in `shared` and are implemented in `security`. |
| Job queue | Lives in `shared.jobs`. Each module plugs in through a `JobHandler`. The worker is switched on by `reconflow.jobs.worker.enabled`, which the `worker` profile sets. |
| Normalization | Rules N1–N11 in `reconciliation-rules.md` are the single source of truth. References are trimmed, NFKC-normalized and upper-cased with no internal characters removed. `transaction_date` is the UTC date of `transaction_at` when present. |
| Discrepancy key | `<TYPE>:<reference>:<transaction_type>:<currencies>`, with no run or period in it. |
| Exceptions API | The engine creates cases through `exceptions.DiscrepancyRecorder`, in the same transaction as each day's chunk. |
| Pagination | `page`/`size`/`sort`, default 50, max 200 (larger values are clamped), sort fields whitelisted. `/transactions` uses a `Slice`. |
| Storage config | `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY` and `S3_SECRET_KEY`, with bucket `reconflow-imports`. |
| Tests | JUnit 5, AssertJ, Testcontainers PostgreSQL via `@ServiceConnection`, jqwik for property tests, k6 for load tests. Each test creates a fresh organization; there is no `TRUNCATE` and no `@Transactional` on tests. |
| Git | Conventional Commits with task IDs, e.g. `feat(ingestion): M5.11 row validator` on branch `feat/M5.11-row-validator`. |

## How to work through a phase

1. Read sections 1–3 of the plan, and look up any concept you can't yet explain out loud.
2. For each task, create the branch, build it, and check the *Done when* line before opening the PR.
3. Apply the cross-cutting checklist at the bottom of TASKS.md to every PR.
4. When a phase is finished, answer its interview questions without looking at the model answers. The ones you can't answer show you what to revisit.
5. Tick the tasks in TASKS.md and update the plan's **Status** line.
