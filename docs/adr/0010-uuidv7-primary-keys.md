# 0010. UUIDv7 primary keys, generated in the application

- **Status:** Accepted
- **Date:** 2026-11-16
- **Tasks:** TASKS.md M2, M5.14, M6.1

## Context

Every table needs a primary key. The IDs appear in URLs (`/exceptions/{id}`), travel between modules, and are inserted at high volume (1.5 million `transaction_record` rows a day, written in JDBC batches of 500 to 5,000). PostgreSQL 16 has `gen_random_uuid()` (version 4) but no `uuidv7()`; that arrives in PostgreSQL 18.

## Decision

We will use **UUIDv7** for every primary key, **generated by the application** before insert. V1 deliberately has no `DEFAULT` on id columns. For set-based `INSERT … SELECT` inside the database (the matching engine), the M6 migration adds a `uuid_generate_v7()` SQL function that produces the same layout; a test checks that IDs from both sources report version 7.

UUIDv7 puts a 48-bit Unix-millisecond timestamp in the high bits, followed by random bits.

## Consequences

- IDs are globally unique without coordination, so a batch of rows can be built in memory with their IDs and inserted in one round trip, and IDs can be assigned before a related object (the storage key of an upload uses the batch ID before the row exists).
- They're safe to expose: not sequential, so counts can't be inferred and neighbours can't be enumerated (tenant checks still apply; IDs aren't secrets).
- Roughly time-ordered, so B-tree inserts land near the right edge of the index instead of on random pages: fewer page splits and better cache use than UUIDv4 at high insert rates.
- 16 bytes per key instead of 8 for `BIGINT`, in every index and foreign key. Acceptable at this scale.
- The creation time is readable from the ID. Not sensitive here, but worth knowing.
- When PostgreSQL 18 is adopted, the custom SQL function can be swapped for the built-in one.

## Alternatives considered

- **`BIGSERIAL` / identity columns.** Compact and ordered, but sequential IDs leak business volume and are trivially enumerable in URLs, and the ID is only known after an insert round trip, which gets in the way of batching and of assigning IDs before insert. Rejected.
- **UUIDv4 (`gen_random_uuid()`).** Unique and unguessable, but random: at hundreds of millions of rows, inserts scatter across the whole index, causing page splits and cache misses. Rejected.
- **Database-generated UUIDv7 as a column default.** Not available in PostgreSQL 16 without an extension or a custom function on every insert path, and it would bring back the round trip. Revisit with PostgreSQL 18.
- **ULID / Snowflake IDs.** Similar properties, but non-standard formats that need custom types or text columns. UUIDv7 is standardized (RFC 9562) and fits the native `uuid` type. Rejected.
